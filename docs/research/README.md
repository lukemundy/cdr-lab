# Research notes

These notes record research that supports the requirements in each service `DESIGN.md`. Each note gives its research date, the versions it applies to and its primary sources. Each fact has a citation.

The CDR standards, rules and the products in these notes change. Before you depend on a fact, check its source again. When a note is out of date, add a new dated note. Do not edit the old note.

## Main findings

- The production Register does not always follow the CDS or RFC 9110. For example, its ETags have no quotes, and it does not return `x-fapi-interaction-id`. Observed production behaviour is background only. The [specification conventions](../spec/conventions.md#sources-for-requirements) give the sources for requirements.
- The ACCC mock Register is not a reliable model of production behaviour. It does not implement Get Data Holder Brands Summary. Its certificate-bound tokens use a SHA-1 thumbprint, and its token endpoint checks only the certificate common name. Use it only as a black-box reference for the API contract.
- The CDS 1.36.0 sources disagree about Register error codes. The CDS Known Issues section admits this. The ACCC Developer Portal describes what the production Register does.
- The CDS gives no non-functional requirements for the Register itself. It sets requirements only for the participants that call the Register, for example that data holders react to status changes within 5 minutes.
- No open-source general-purpose auth server supports the CDS-specific data holder features without custom code. `luikyv/go-oidc` (Go) and `panva/node-oidc-provider` (Node) are the best candidates. Ory Hydra and zitadel/oidc do not support mTLS certificate-bound tokens.
- New versions of five banking endpoints (Get Accounts, Get Account Detail, Get Bulk Balances, Get Transactions For Account and Get Transaction Detail) become binding on 9 November 2026. The CDS 1.36.0 OpenAPI specification describes only the new versions.
- The OIDC hybrid flow is retired. A data holder supports only the authorisation code flow with PAR, PKCE and JARM. The CDS 1.36.0 examples still show hybrid flow items, and some examples do not agree with the normative text.
- The CDS does not say what a data holder does at registration, at PAR or at a token refresh for a software product that is not ACTIVE. No source says how a test system gives a one-time password to a consumer.
- The ACCC mock Data Holder is a narrow reference. It implements 2 of the 19 banking operations and no product reference data. Its certificate-bound tokens use a SHA-1 thumbprint from a request header, and it checks the one-time password only in the browser.
- The CDS accessibility standard does not require WCAG 2.1 AA. "WCAG 2.1" in the CDS is Guideline 2.1 (Keyboard Accessible). The standard names five WCAG guidelines, with no version and no conformance level, and says only "MUST seek to comply". The AHRC recommends WCAG 2.2 AA.
- WCAG 2.2 SC 3.3.8 applies directly to the data holder OTP page: the consumer must be able to paste or autofill the code, so one input box for each digit fails.
- Most critical JS framework advisories of 2025 and 2026 are in server code (React Server Components, Next.js middleware and server functions). A static SPA build does not contain this code.
- RFC 10017 (August 2026) strongly recommends a Backend for Frontend for browser apps that handle personal data. No token goes to the browser.
- Cookies are not isolated by port, and all lab UIs are on `localhost`, so `SameSite` does not separate them. Go `http.CrossOriginProtection` refuses `same-site` requests, so it does.
- Script blocking and a release-age delay in the package manager stop almost all npm supply-chain incidents of 2025 and 2026. Valid provenance did not stop three of them.
- Go does not ignore `node_modules`. A JS workspace in the repository needs an `ignore` directive in `go.mod`.
- No public CDR data holder mock has an operator UI. A withdrawal by staff is the alternative method of rule 4.25(1)(b), and the data holder must record how the consumer asked for it (rule 9.3(1)(b)).
- A CDR server certificate belongs to a data holder brand. In CDS 1.36.0, no data recipient endpoint is MTLS, and a data recipient needs no server certificate. The Participant Portal refuses a server CSR whose CN is not a host name, but it only warns when the O is not the brand name or the legal entity name.
- A revocation request identifies the certificate and gives a reason (CP 4.9.3). The CA issues a CRL at least once every 24 hours, also with no changes (CP 4.9.7). No source says if a revocation removes a client certificate from a software product on the Register.
- The CDS has no rule for the brand of a data holder on its own authentication and consent pages. The DSB CX Guidelines speak only of the brand name of the data recipient. The friction standard forbids links to other documents and services, so a branded page cannot have the usual footer of a bank.
- One instance for each brand meets the CDS rule of a separate issuer for each brand. The Register gives `legalEntityName` a maximum length of 36 characters.
- `.example` breaks the rule that no preset name contains "Example". RFC 6761 reserves `.test` for tests.
- The data holder fields of today support a catalogue of five or more product categories, but not rate tiers, eligibility or constraints.
- The four major banks use proprietary fonts, except NAB. Their own stylesheets give brand colours that differ from those of third-party colour sites.
- With the bank colours, each text pair of the candidate palettes passes WCAG 2.2 AA. A yellow primary button on a white card has a contrast of 1.51:1, which SC 1.4.11 permits for a button with a text label.
- No source requires the data holder to send an email to the consumer when a consent ends. The notice of rule 4.26A goes to the accredited person, and the data holder sends it as an HTTP request.
- The CDS requires each consumer-facing communication of a data holder to state that third parties do not need the passwords of the consumer. The OTP email of the lab does not state this yet.
- Most email clients do not support CSS variables or OKLCH colours. A branded email needs inline styles with literal sRGB values.
- Mailpit serves an inline SVG part as `application/octet-stream`, so the lab mail sink does not show an SVG logo in a `cid:` part. An inline PNG part works. Go has no SVG rasteriser in the standard library.
- Compose returns an error when a service refers to a service that the active profiles ignore. A `depends_on` entry with `required: false` gives only a warning. Thus a service with no profile must not depend on a profile service.
- All data holder brands share the application role `dataholder_app`, because a PostgreSQL role is global to the cluster. Each service user can connect only to its own database.
- The PostgreSQL image runs `init.sql` only on an empty data directory. A database that only a profile creates is not there when a lab turns the profile on later.
- `down` removes only the containers of the services of the Compose file. `--remove-orphans` also removes the containers of a renamed or removed service.
- ADR 0014 and the design guide already make a data holder consumer UI a React SPA. Go pages for the site need a new ADR.
- The public listener gives CORS `*` to each path except the authorisation path, and sends each unknown path to a CDS JSON error. A separate lab-only listener for the site needs no exception in the CDR listener.
- A `__Host-` cookie always has `Path=/`, and cookies are not isolated by port. In the lab, no port or path separates a session cookie of the site from the CDR pages.
- A site API on `app.ProductReader` gives the same data as Get Products and Get Product Detail by construction. The data holder holds no eligibility, constraints or application URI for a product.
- The CDS requires each consumer-facing interaction of a data holder to state that third parties do not need consumer passwords. The site must have this statement.
- A sign-up can reuse the customer use case of the operator. Customers are rows, not events, and no rule reads the channel of a sign-up. A customer with no open account cannot give a CDR consent.
- Cookies are not isolated by port. A session cookie with one name at the four lab banks on `localhost` replaces the session of a different bank.
- `http.CrossOriginProtection` of the site listener is the CSRF control that OWASP calls primary for modern browsers. It also stops login CSRF.
- A session time limit for security is a time limit of the content under WCAG 2.2 SC 2.2.1. The 20-hour exception applies only to a limit that is longer than 20 hours.
- `Clear-Site-Data: "cookies"` removes the cookies of each lab UI on `localhost`, also a CDR flow in progress.
- The CDS Restricted Credentials text forbids a memorised secret as the single factor for LoA 2. It does not say "never ask for a password".
- A site use case on the domain balance function and the transaction query of a consent gives the same data as the CDS APIs by construction.
- No CDS account schema has a product ID. The category and the name of the product give the required fields, so an account needs no link to a product.
- The CDS puts the product categories into deposit products and lending products. In real life, a lending product needs an assessment of the credit contract before it opens.
- The data holder has no BSB of its own now. A `bsb` field in `brand.json` is a change of the strict contract of the brand directory.
- A close on the site through the close use case of the operator has the same effects by construction: the end of each consent for the end of eligibility, the backstop job and the notice. No source gives a balance rule for a close.
- The ACCC says that a closed account that the data holder does not share shows on a new consent as not selectable, with a reason. The consent page hides closed accounts now.
- Rule 1.15(3)(f) with rule 7.9 requires the dashboard to show what CDR data was disclosed, when, and to which data recipient, for each data cluster with the first and the last date. The data holder has no record of disclosures now.
- The domain already records a withdrawal method in `ArrangementWithdrawn`. A second method value meets ADR 0021, because no rule of the mock acts differently on the method.
- The CDS requires two messages in the withdrawal on the dashboard (consequences, redundant data) and one message on the dashboard (check with the data recipient). The DSB gives suggested text and leaves the wording to the data holder.
- The ACCC says that the dashboard obligation ends with eligibility. Showing the dashboard to a customer with no open account is permitted.
- Rule 4.24(d) forbids a reference to a different document in the authorisation process, so the instructions to withdraw on the consent page are text with no link.
- The data holder has no CDR policy, and rule 7.2(8) applies to each online service of the data holder.
- The Register image is published when only the browser tests of its console pass. The Go and conformance tests do not gate it, and its path filter skips commits that change only Go code outside the console.
- The data holder image job builds with no commit in the binary, because it does not use `mise run up`.
- A data holder becomes ready only after it gets the software product statuses from a Register that it trusts. A verification on a cluster needs a Register.
- ADR 0018 is not correct about Renovate: one group updates the Node of `mise.toml` and the Node image together.
- A Register from the chart starts with no participants. The data holder chart already has the pattern for a seed: a `seed -if-empty` init container after `migrate`, as the service user, with an existing ConfigMap mounted as a directory.
- A seed with placeholders does not load, because each URI of a participant must be an absolute `https` URI with a host. An example seed with `.test` hosts loads and a test can prove it.
- A data holder brand needs no certificate on the Register at seed. The seed is a precondition of the issue of its CDR server certificate by the Register.
- Get Data Holder Brands Summary proves the brands without a token, but only with the public base URI. The full endpoints need Get Data Holder Brands (mTLS and a software product token) or the console API.
- cocogitto gives the next version and the release notes from the tags and the Conventional Commits, with no commit to `main`. On 0.x, a breaking change gives a minor bump, and cog has no setting to change this. Squash merges keep only the PR title, so a commit footer cannot mark a release that needs a fresh deployment.
- The cert-manager CA issuer cannot replace the Register as the CDR issuer without a second copy of the intermediate key, and an external issuer needs cluster-wide changes. The existing Register issue path, a CLI command and a CronJob give issue and renewal in a cluster and in compose. The services load their certificates only at start.
- `TLSRoute` passthrough is in the Gateway API Standard channel since v1.5.0, and ingress-nginx is retired. The services call back to the conformance suite, so in a cluster the suite runs as a Job in the cluster.
- No CDR rule applies to the sign-up of a data recipient. The Privacy Act APPs apply, and rule 7.2 requires a separate CDR policy in each online service.
- NIST SP 800-63B-4 requires 15 characters at least for a password that is the single factor. Schedule 2 control (h) names password complexity and ageing, which ASVS 5.0 and NIST forbid.
- The design system has no dark theme, and ADR 0025 has no listener for the web app of a data recipient.
