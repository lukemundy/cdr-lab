# Production gaps

This file lists the shortcuts that are acceptable in the lab and that a production service could not operate with. It is not a plan, and its entries are not tickets.

## Rules

- An entry is a choice that we made because it is easy, and that a production service could not operate with. A function that a project put out of scope is not a gap.
- Add the entry in the change that takes the shortcut. Remove the entry in the change that closes the gap.
- One line for each gap. The file has no history, no priority and no status.
- A real component never imports a `pkg/` library, but it can copy or fork one. A gap in `pkg/` then goes into the copy, so its entry gives what the copy needs.

## Shared libraries (`pkg/`)

| Shortcut | Why it is acceptable in the lab | What a production service needs | Where |
|---|---|---|---|
| A data holder authorisation server keeps its authorisation sessions (pushed requests, and flows in progress) in the memory of the process, with a limit of 10,000 sessions. | The lab runs one instance of each data holder, and a flow that ends at a restart is acceptable there. | A store that all instances share and that stays after a restart, with a limit for each client. | `pkg/authserver/sessions.go` |
| The trace, metric and log providers shut down in sequence with one time limit for all three. | The lab telemetry backend is local and fast, so each provider completes in the limit. | A limit for each provider, or a shutdown of the three at the same time, so that a slow export of one signal does not stop the flush of the others. | `pkg/platform/telemetry`, and `telemetryShutdownTimeout` in each `cmd` |
| The revocation check of an mTLS listener checks only the client certificate, not each certificate in the chain that the CDS requires ([CDS: Certificate Validation](https://consumerdatastandardsaustralia.github.io/standards-archives/standards-1.36.0/#certificate-validation)). | The lab never revokes a CA certificate ([PKI: Non-goals](../pki/DESIGN.md#non-goals)), and the mock CDR intermediate signs each lab client certificate. | A check of the revocation status of each certificate in the chain, through the CRL or the OCSP responder that each certificate identifies. | `pkg/cds` revocation check, and the revocation check of the Register |
| The event codec reads only schema version 1 and refuses payload fields that the Go type does not have. No code reads earlier payloads, so a change to an event payload needs a lab reset. | Lab data lasts only until the next reset or CI run, so no stored event has an earlier payload. A cluster deployment keeps its data across an upgrade, but a release that changes an event payload says that it needs a fresh deployment ([ADR 0028](adr/0028-find-the-need-for-a-fresh-deployment-from-the-migrations-and-the-event-golden-files.md)). | Rules for changes to payloads that keep the stored events readable, for example a weak schema or schema versions with code that reads the earlier versions, so that also an older build can read the events of a newer build after a rollback. | `pkg/eventsourcing` JSON codec |

## All services

| Shortcut | Why it is acceptable in the lab | What a production service needs | Where |
|---|---|---|---|
| The operator interface has one static bearer token for all operators, over plain HTTP. The token is public in `compose.yaml`, and in a cluster deployment it is in a Secret that each operator of the namespace can read. | The lab data has no value, and all operators of one lab have the same trust. In the lab, the port binds to `127.0.0.1` only. In a cluster deployment, the umbrella chart routes no path of the internal listener outside the cluster except the CRL, so an operator reaches it only through `kubectl port-forward`, which Kubernetes RBAC controls. The interface refuses each request whose `Host` header is not in `INTERNAL_ALLOWED_HOSTS`, so that a web page cannot use DNS rebinding to reach it. | TLS, an identity for each operator, and a record of each operator action. | `pkg/platform/operatorhttp`, `adapter/operatorapi` of each service |
| The operator console has no login and gives the browser no credential, over plain HTTP. Any process on the host can use it, and in a cluster deployment each person who can port-forward in the namespace. The console of the data holder shows consumer data: names, email addresses and customer numbers, which are also the user identifiers of the consumers. | The console is off by default, all operators of one lab have the same trust, and all consumer data of the lab is invented. A cluster deployment exposes the console only through `kubectl port-forward`, or through an auth proxy that the team adds. The console refuses each request whose `Host` header is not in `INTERNAL_ALLOWED_HOSTS`, so that a web page cannot use DNS rebinding to reach it. The `127.0.0.1` binding and the refusal of changes from other origins do not stop a web page alone, because DNS rebinding goes around both. | TLS, a login with an identity and a session for each operator, and a record of each operator action ([ADR 0014](adr/0014-web-uis-as-embedded-react-single-page-applications.md)). | `pkg/platform/consolehttp`, `adapter/console` of each service |
| The private signing keys are in the service database with no encryption. | The repository must contain no keys, and the lab keys protect no real data. | Keys in a key management service or a hardware security module, where the service cannot read the private part. | `signing_keys` table of each service |
| The connection to PostgreSQL has no TLS, and the database has no encryption at rest. This includes the CDR data that a data recipient collects, which Schedule 2 of the CDR Rules requires to be encrypted at rest. | All data of the lab is invented. In the lab, the database is on the lab network of one host. In a cluster deployment, the database is in the cluster of the team. | TLS to the database with server verification, and encryption at rest. | `PGSSLMODE` in `compose.yaml`. The Register chart can use TLS, but it cannot give the CA to verify the server. |
| With the TLS passthrough routes of a cluster deployment, the services see the address of the Gateway as the client address, not the address of the participant. | The lab has no rule that depends on the client address, and the address in telemetry then shows only the Gateway. | The client address from the Gateway, for example through the PROXY protocol, for the logs and the limits of each client. | the TLSRoutes of `charts/cdr-lab` |
| No endpoint has a rate limit. For example, the sign-in of a data recipient has no limit of failed sign-ins for a member. | The lab has no traffic that the services do not expect. A cluster deployment serves only the teams that share it, and a team can make a fresh deployment. | Limits for each client and each endpoint. For a data holder, the CDS traffic thresholds give the minimum. | all HTTP listeners |
| The data holder and the data recipient send email over SMTP with no TLS and no authentication. | The SMTP server is the mail sink on the lab network, or a mail sink that the team runs in its cluster. All email of the lab goes to invented addresses. | TLS to the mail server, with authentication. | the mailer of the data holder and of the data recipient |

## Register

| Shortcut | Why it is acceptable in the lab | What a production service needs | Where |
|---|---|---|---|
| The Register reads the private key of the mock CDR intermediate CA from a file, with no key management service or hardware security module. In the lab, any user on the host can read the key file. In a cluster deployment, the key is in a Secret that each person who can read Secrets in the namespace can read. | The key signs only lab certificates, and the lab data has no value ([ADR 0022](adr/0022-run-the-mock-cdr-intermediate-ca-in-the-register.md)). `mise run reset` deletes the key. In a cluster deployment, only the Register pod mounts it ([ADR 0032](adr/0032-issue-each-cdr-certificate-of-a-deployment-through-the-register-and-renew-it-with-no-manual-step.md)), and a fresh deployment deletes it. | A CA key in a key management service or a hardware security module, where the service cannot read the private part. | `CDR_INTERMEDIATE_KEY_FILE` in `compose.yaml`, the CA set-up of `cli/cdrlab` |
| The Register refuses a client assertion with a Data Recipient Brand ID as the client ID. It accepts only the Software Product ID, but the CDS requires that it supports both ([CDS: Data Recipients calling the CDR Register](https://consumerdatastandardsaustralia.github.io/standards-archives/standards-1.36.0/#data-recipients-calling-the-cdr-register)). | Each lab client uses its software product ID. The CDS will deprecate the brand ID ([Register: only the software product ID as the client ID](../services/register/design/authorisation-server.md#reg-0480)). | Support for the brand ID as the client ID, with a rule for the JWKS and the client certificates of a brand that has more than one software product. | `adapter/idp` of the Register |
| The Register reads the client certificate only from its own TLS connection. It has no setting for a proxy that terminates TLS and gives the certificate in a header ([Register: the client certificate only from the TLS connection](../services/register/design/register-apis.md#reg-0351)). | The lab and the Register chart connect each client directly to the Register, with no proxy between them. | A setting for a trusted proxy that terminates TLS, and a header from that proxy only, with the certificate. | `adapter/httpapi` of the Register |
| The Register chart runs one pod and stops it before it starts the new pod, because the Register is the issuing CA. Each upgrade or restart stops the Register. | The lab has no users that a short stop affects. The teams that share a cluster deployment accept a short stop at each upgrade, and an upgrade can need a fresh deployment before version 1.0.0 ([ADR 0027](adr/0027-release-all-artifacts-with-one-version-from-a-manual-workflow-on-main.md)). | More than one instance with one CRL signer, so that an upgrade keeps the Register available. | `charts/register`, `charts/cdr-lab` |

## Data holder

| Shortcut | Why it is acceptable in the lab | What a production service needs | Where |
|---|---|---|---|
| The data holder chart runs one pod and stops it before it starts the new pod, because the authorisation sessions and the online bank site sessions are in the memory of the process. Each upgrade or restart stops the brand, and ends each authorisation flow and each session. | The lab has no users that a short stop affects. The teams that share a cluster deployment accept a short stop at each upgrade. | Shared session stores, so that more than one instance serves the brand during an upgrade. | `charts/dataholder`, `charts/cdr-lab` |
| The authorisation codes and the refresh tokens are in the database in plain text. | The lab tokens give access to invented data only. The authorisation server library reads the refresh token back at the code exchange, so a hash from the start is not possible. | Encryption of the two values with a key that the database does not have, or a hash of each value after its last read. | `grants` table of the data holder |
| The data holder never removes a grant, also after its code and its refresh token expire. | A reset of the lab removes all grants. | A removal of each grant that no token request can use. | `adapter/grantstore` of the data holder |
| The data holder sends the one-time password by email. The CDS permits only the authenticator types of the Digital ID standards, and an OTP by email is not one of them ([data holder: the OTP by email](../services/dataholder/design/consumer-authentication.md#dh-1276)). | The mock data holder keeps the OTP by email on purpose, because it makes testing and automation simpler: lab users, scripts and the tests read the OTP from the mail sink with no manual step. All customers are invented, and no real mailbox receives an OTP. | An authenticator type of the AL Table of the Digital ID standards, for example an OTP by SMS to a verified mobile number. | `adapter/smtpmail` and `domain.Authentication` of the data holder |
| The limits of the one-time password (3 sent, 3 incorrect entries) are for one authorisation flow only. A client can start many flows for one customer. | Only registered lab software products can start a flow, and the mail sink delivers no email. | Limits for each customer across flows, for the emails and for the incorrect entries. | `domain.Authentication` of the data holder |
| The online bank site signs in a consumer with the email address or the customer number only. Its password field accepts any value, and the UI does not send the password. A session has no inactivity timeout. | The site is off by default, all customer data of the lab is invented, and the sign-in page says that any password works. The CDR authentication does not use the site, and it still asks for the email address or the customer number, and a one-time password. | Real authentication of the consumer: a credential that the bank verifies, multi-factor authentication, limits on failed sign-ins, and an inactivity timeout. | `adapter/banksite` of the data holder |
| The online bank site keeps its sessions in the memory of the process, with a limit of 10,000 sessions. A restart ends each session. | The lab runs one instance of each data holder, and a consumer who signs in again after a restart is acceptable there. | A session store that all instances share and that stays after a restart, with a limit for each customer. | `adapter/banksite` of the data holder |
| The online bank sites, the web apps of the data recipients, the consoles and the CDR pages of the lab share the host `localhost`. Cookies are not isolated by port, so the browser sends the session cookie of each site to each lab service on that host. | All lab ports bind to `127.0.0.1`, each other lab service ignores the cookie, and all customer data of the lab is invented. The cookie name has the brand ID, so the site of each bank reads only its own cookie. | A host of its own for each site, so that the browser sends the session cookie only to that site. | `compose.yaml` |

## Data recipient

| Shortcut | Why it is acceptable in the lab | What a production service needs | Where |
|---|---|---|---|
| The web app keeps its sessions in the memory of the process, with a limit of 10,000 sessions. A restart ends each session, and the chart runs one pod and stops it before it starts the new pod. | The lab runs one instance of each brand, and all members of the lab are invented. A member who signs in again after a restart is acceptable. | A session store that all instances share and that stays after a restart, with a limit for each member. | the web app of the data recipient, `charts/datarecipient` |
| A sign-up and a password reset send their email in the request. The time of the response then shows whether a member has the email address. | All members of the lab are invented, and the status and the body of the response are the same for each address. | An email from a background job, so that the time of each response is the same. | the sign-up and the password reset of the data recipient |
| A session of the web app has no inactivity timeout. It ends 24 hours after its start. | All members of the lab are invented, and a session ends when the browser closes. | An inactivity timeout, with a warning and an extension before it ends. | the web app of the data recipient |
| The access tokens and the refresh tokens of each connection are in the database in plain text. | The lab tokens give access to invented data only, and each token is bound to the client certificate of the software product, so a copy of the database alone cannot use it. | Encryption of the tokens with a key that the database does not have, for example from a key management service. | the token table of the data recipient |
